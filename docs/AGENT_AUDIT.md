# Agent and Account-Selection Audit (Phase 1)

## Scope and evidence

This was a read-only Phase 1 audit of the repository before Phase 2 implementation. No runtime behavior was changed during the audit, and `.env` was not inspected. The findings below describe that baseline and are superseded where noted by the Phase 2 implementation status.

**BLOCKED — archive comparison:** The agent ZIP archives referenced in the supplied instructions were not available in the checked-out workspace. The audit therefore traces the repository source, not the contents or differences of those archives. Source modules previously noted as potentially missing—including market review, execution, real-store, market data, and terminal UI code—are present in this checkout. Archive-specific conclusions require the original archives.

**BLOCKED — live account/report verification:** This audit did not connect to Deriv or query live qualification or settlement data. Metrics and readiness results in the user-supplied report are treated as supplied evidence, not independently verified facts.

No account identifiers, credentials, or environment values are reproduced here.

## Executive summary

- The selected account is React application state. The browser sends its account ID with each request; the API re-fetches Deriv-linked accounts and resolves the requested account on the server. There is no shared server-side “currently selected account.”
- Real-account orders have server-side gates: a global live-execution switch, an exact-account confirmation value, and a stored, unexpired qualification that passes the live-readiness gate. Demo accounts do not require those real-money gates.
- Entry behavior differs materially by path. Bot/automatic entries analyze market candles; direct terminal Buy/Sell requests set direction directly and skip candle analysis and its signal/volatility filters. Both still encounter portfolio, drawdown, loss-streak, daily-loss, and reservation checks.
- Several limits are duplicated across backend, frontend previews, and SQL. The most consequential inconsistencies are the 1% stake formula, the USD absolute cap, the automatic USD $10 cap, the two-open-contract limit, the 10% drawdown limit, and the 75-point signal threshold.
- Strategy and exit evidence are best-effort audit writes after order confirmation. Report evidence is joined by contract ID; there is no transaction-ID reconciliation in the inspected intent/audit path. Missing intent or audit rows therefore result in “Unavailable” report fields.

## 1. Account selection and real-money controls

### Selection and propagation

- `App.jsx` keeps `selectedAccountId` in component state and derives the selected account from the fetched accounts list. It passes that same selection into Bot Agents and the Trading Terminal. The state is not persisted as a server-wide active account. ([App.jsx](../frontend/src/App.jsx#L46), [App.jsx](../frontend/src/App.jsx#L149), [App.jsx](../frontend/src/App.jsx#L207))
- Account choices display the Deriv account ID without masking. Switching uses a generic confirmation dialog; it says Bot Agents will pause monitoring, but does not state whether the new account is real-money, check for open positions, or require those positions to expire first. ([App.jsx](../frontend/src/App.jsx#L189), [App.jsx](../frontend/src/App.jsx#L232), [App.jsx](../frontend/src/App.jsx#L235))
- The Bot Agents component is keyed by the selected account ID, so a switch remounts it. Its timer effects are cleaned up locally; the switch handler does not call the server stop endpoint. The persisted control record for the previous account can therefore remain active even though its browser scheduler has stopped. ([App.jsx](../frontend/src/App.jsx#L207), [TradeAgent.jsx](../frontend/src/agents/trade-agent/TradeAgent.jsx#L485), [TradeAgent.jsx](../frontend/src/agents/trade-agent/TradeAgent.jsx#L588))
- Each API request includes an account query value. The backend obtains the linked-account list from Deriv and resolves the requested ID against it before agent and portfolio operations. This is per-request validation, not shared active-account state. ([app.js](../backend/api/src/app.js#L85), [app.js](../backend/api/src/app.js#L94), [app.js](../backend/api/src/app.js#L103), [deriv.js](../backend/api/src/providers/deriv.js#L19))

### Real vs. demo eligibility

- `canTradeAccount()` allows valid demo accounts; real accounts require `LIVE_TRADING_ENABLED === 'true'` and `LIVE_TRADING_CONFIRM` to equal the selected account ID. The real-account confirmation is enforced on the server. ([account/index.js](../backend/trading/agents/account/index.js#L9), [account/index.js](../backend/trading/agents/account/index.js#L12))
- The frontend receives only the global execution-enabled flag for its real-money blocker. It does not show a separate account-specific confirmation or qualification state in the account-switch dialog. The server remains the final gate. ([app.js](../backend/api/src/app.js#L49), [App.jsx](../frontend/src/App.jsx#L207), [TerminalOrder.jsx](../frontend/src/components/TerminalOrder.jsx#L43))
- Before a real buy, `executeRealOrder()` reads the account-scoped qualification row and requires approval metadata, an unexpired time window, valid evidence, and a passing live gate. Missing/unreadable qualification fails closed. ([execute.js](../backend/trading/execute.js#L171), [execute.js](../backend/trading/execute.js#L177), [real-store.js](../backend/trading/real-store.js#L304))
- The live gate requires 500 settled trades across 3 distinct weeks, no more than 50% on one day, positive verified after-cost net P&L, profit factor at least 1.2, win rate above break-even, a positive verified holdout with at least 100 trades and predictive performance, strategy on every trade, and reconciliation on every trade. The gate evaluates aggregate performance; it does not impose a separate pass per strategy or an explicit rehearsal check. ([live-gate.js](../shared/live-gate.js#L4), [live-gate.js](../shared/live-gate.js#L34), [live-gate.js](../shared/live-gate.js#L68))

### Analysis mode differences

- The analysis score is a weighted rule score, not a calibrated probability. Its component weights are 20, 25, 20, 20, and 15 points; scores can reach 100 when criteria align. ([agent-analysis.js](../shared/agent-analysis.js#L55))
- The shared analysis and backend risk module both use a 75-point direction threshold. Automatic entry separately requires 85 points and volatility rank no greater than 0.8. For volatility rank below 0.2, the automatic strategy is labelled “Low-volatility breakout” and additionally requires a 90-point score and a breakout. ([agent-analysis.js](../shared/agent-analysis.js#L6), [risk/index.js](../backend/trading/agents/risk/index.js#L11), [agent-analysis.js](../shared/agent-analysis.js#L107), [market-review.js](../shared/market-review.js#L44), [market-review.js](../shared/market-review.js#L50))
- Bot Agents “Manual Setup” is not the same as a manual terminal direction: it disables automatic-only filters, but still analyzes candles and uses the 75-point direction threshold. Direct terminal Buy/Sell skips that analysis entirely. ([TradeAgent.jsx](../frontend/src/agents/trade-agent/TradeAgent.jsx#L192), [trade-agent/index.js](../backend/trading/agents/trade-agent/index.js#L446))
- Automatic mode uses a 300-second analysis interval, a 45-second entry check interval, and up to 10 candidate markets. Exit monitoring is scheduled on a 15-second interval. Demo automatic mode can auto-start; the component does not auto-start real accounts. ([agent-analysis.js](../shared/agent-analysis.js#L100), [TradeAgent.jsx](../frontend/src/agents/trade-agent/TradeAgent.jsx#L218), [TradeAgent.jsx](../frontend/src/agents/trade-agent/TradeAgent.jsx#L470))

### Duplication and drift risks

1. **Stake formula is duplicated.** Backend `calculateStake()` is the execution authority, while TerminalOrder and FinanceAccountAgent independently reproduce balance × 1%, rounding, and currency precision. A future change can make the displayed stake differ from the submitted stake. ([risk/index.js](../backend/trading/agents/risk/index.js#L43), [TerminalOrder.jsx](../frontend/src/components/TerminalOrder.jsx#L37), [FinanceAccountAgent.jsx](../frontend/src/agents/finance-account/FinanceAccountAgent.jsx#L5))
2. **The absolute $20 cap is not enforced by the SQL reservation function.** Current agent calls calculate a capped value before reservation, and SQL also checks 1% of balance; however, the database rule itself does not encode the absolute cap. Direct callers of the reservation RPC are not independently constrained to $20. ([agent-analysis.js](../shared/agent-analysis.js#L7), [real_execution.sql](../backend/deriv_execution/real_execution.sql#L269))
3. **The automatic $10 limit is semantically overloaded.** It is both maximum automatic USD stake and the open-contract loss trigger, while the Finance preview repeats `10` as a literal. The terminal preview uses the shared setting. ([agent-analysis.js](../shared/agent-analysis.js#L103), [trade-agent/index.js](../backend/trading/agents/trade-agent/index.js#L367), [trade-agent/index.js](../backend/trading/agents/trade-agent/index.js#L490), [FinanceAccountAgent.jsx](../frontend/src/agents/finance-account/FinanceAccountAgent.jsx#L16), [TerminalOrder.jsx](../frontend/src/components/TerminalOrder.jsx#L40))
4. **The 75-point direction threshold has two code definitions plus UI copy.** `shared/agent-analysis.js` and backend `risk/index.js` define it independently; TradeAgent also renders a literal “75/100”. Automatic entry's 85-point threshold is a distinct additional rule, not a replacement for the shared direction threshold. ([agent-analysis.js](../shared/agent-analysis.js#L6), [risk/index.js](../backend/trading/agents/risk/index.js#L11), [TradeAgent.jsx](../frontend/src/agents/trade-agent/TradeAgent.jsx#L242))
5. **The database repeats open-contract, drawdown, and exit-setting limits.** These must stay synchronized with backend risk constants and validation. ([risk/index.js](../backend/trading/agents/risk/index.js#L5), [risk/index.js](../backend/trading/agents/risk/index.js#L10), [risk/index.js](../backend/trading/agents/risk/index.js#L12), [real_execution.sql](../backend/deriv_execution/real_execution.sql#L262))

## 4. Idempotency, broker execution, and audit evidence

- Automated idempotency is based on account, symbol, granularity, and signal epoch. Direct manual directions use account plus a client-generated request UUID; the terminal creates a new UUID on each submission, so a user retry is not deduplicated against the earlier click unless it reuses that UUID. SQL enforces uniqueness of the derived key and blocks unresolved reservation states. ([trade-agent/index.js](../backend/trading/agents/trade-agent/index.js#L500), [TerminalOrder.jsx](../frontend/src/components/TerminalOrder.jsx#L50), [real_execution.sql](../backend/deriv_execution/real_execution.sql#L46), [real_execution.sql](../backend/deriv_execution/real_execution.sql#L286))
- Strategy, score, technical indicators, and exit settings are recorded after a confirmed buy. The audit write is caught and logged rather than making the broker-confirmed order fail. Consequently an order can exist without strategy evidence. ([trade-agent/index.js](../backend/trading/agents/trade-agent/index.js#L574), [real-store.js](../backend/trading/real-store.js#L100))
- The inspected intent/audit path stores broker contract ID but does not store the Deriv transaction ID. Report evidence is joined from settlement contract ID to intent contract ID and then to strategy/lifecycle events. Historical or external trades, absent intent rows, and failed audit writes can produce unavailable strategy/market details. ([real-store.js](../backend/trading/real-store.js#L144), [real-store.js](../backend/trading/real-store.js#L167), [tradeReport.js](../frontend/src/components/tradeReport.js#L46))
- Exit audit records threshold checks and outcomes such as closed, early sale unavailable, and unconfirmed. The close function makes a sell request and considers the presence of `sold_for` a close confirmation; it does not independently confirm the result against a later portfolio/history read or retry the close. This leaves an ambiguous result when the broker response is incomplete. ([trade-agent/index.js](../backend/trading/agents/trade-agent/index.js#L399), [trade-agent/index.js](../backend/trading/agents/trade-agent/index.js#L405), [real-store.js](../backend/trading/real-store.js#L88), [execute.js](../backend/trading/execute.js#L336))
- There is no entry-time eligibility check for future early-sale availability. When an exit threshold is hit but `canSell` is false, the agent records `EARLY_SALE_UNAVAILABLE` and continues watching; binary-contract losses can therefore reach expiry. The account activity UI displays “Wait for expiry” and remaining time when sale is unavailable. ([execute.js](../backend/trading/execute.js#L248), [trade-agent/index.js](../backend/trading/agents/trade-agent/index.js#L399), [trade-agent/index.js](../backend/trading/agents/trade-agent/index.js#L427), [AccountActivity.jsx](../frontend/src/components/AccountActivity.jsx#L181))
- Bot results are browser-local state persisted in `localStorage`; settlements are matched to broker history by contract ID. Account Activity reads broker portfolio/history separately. The Bot results card is useful for in-browser tracking but is not itself a complete authoritative reconciliation ledger. ([TradeAgent.jsx](../frontend/src/agents/trade-agent/TradeAgent.jsx#L74), [TradeAgent.jsx](../frontend/src/agents/trade-agent/TradeAgent.jsx#L116), [TradeAgent.jsx](../frontend/src/agents/trade-agent/TradeAgent.jsx#L670), [AccountActivity.jsx](../frontend/src/components/AccountActivity.jsx#L35))

## 5. Findings for approval

1. **Account switches are UI-only pauses.** Switching unmounts the current Bot Agents component and clears its local timers, but does not call `/api/agent/stop` for the previous account. The server's stored control can remain active, and the confirmation does not check open positions or distinguish real money.
2. **Direct manual terminal Buy/Sell bypasses signal-quality checks.** This is separate from Bot Agents Manual Setup, which still analyzes candles. Manual directions remain subject to exposure and loss controls.
3. **Risk ceilings are not fully represented by one authority.** UI stake previews duplicate sizing; automatic $10 is hardcoded in FinanceAccountAgent and reused as two different controls; the database reservation enforces 1% but not the absolute USD cap.
4. **The configured score is not a win-probability estimate.** It is a weighted indicator score. The source code does not establish that a score of 85 or 100 predicts a particular win rate.
5. **Early sale availability is discovered at exit time, not entry time.** If the contract cannot be sold, the agent records that state but cannot enforce the configured exit threshold before expiry.
6. **Broker reconciliation evidence is incomplete in the inspected trade path.** Strategy evidence is best-effort, report joins use contract ID, and the intent/audit records do not include Deriv transaction ID. The live gate requires reconciled evidence, but this audit found no per-trade broker reconciliation routine in these paths.
7. **Supplied report metrics are not verified here.** The current repository includes a live gate capable of representing nine readiness checks, but this audit did not query its qualification row or independently reproduce the report's account-level measurements.

**Phase 1 complete.** Phase 2 implementation is summarized below; it remains local and requires the SQL migration before deployment.

## Phase 2 implementation status

- Stake sizing is server-authoritative, capped at 1% of balance and $10 USD-equivalent for all order modes. Non-USD orders fail closed when a valid Deriv exchange rate cannot be read.
- A single session-selected account is used across app surfaces. Responses use masked account labels and opaque references; selecting a Real account requires confirmation and audit, and switching is blocked if the current account has open positions or cannot be verified.
- Per-account auto-start is disabled by default. Real-account auto-start requires explicit confirmation.
- Manual terminal Buy/Sell can bypass bot signal qualification only; the live account gate, risk checks, stake cap, and persisted order reservation remain required.
- Order intents retain strategy, score, technical snapshot, decision time, masked account reference, broker transaction ID, and buy price where supplied. Broker settlements update outcomes. Close status is checked with Deriv and remains `unconfirmed` if broker confirmation is unavailable.
- Automated tests use mocked broker responses only. The Deriv exchange-rate WebSocket request has not been verified against a live session; non-USD trading must remain blocked if Deriv rejects it.
- `backend/deriv_execution/real_execution.sql` must be applied to the intended database before using these database-backed features. No hosted database, commit, push, or deployment was performed during this implementation.
